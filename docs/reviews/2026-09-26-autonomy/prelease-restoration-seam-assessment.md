# Read-only assessment: pre-lease restoration preparation

2026-09-26. Separate from the daily per-node feasibility/resource screen. No source changes, fixture run, new proof or architecture implementation.

**There are established preparation/capture/resolve/fresh-recheck seams, but no existing factory seam that carries their qualified results across writer-lease acquisition unchanged. Moving substantial owned restore work before acquisition would require a separate contract decision.** This is not a claim that every pure optimization is impossible.

## Actual order and existing precedents

- `apps/trader/continuous_simulation_factory.py:226` already validates configuration and reads/decodes/verifies the retained inputs, venue model and producer map before acquisition. It opens the existing account database, checks schema revision and HALTED control, then acquires at `:303`. Graph construction follows and injects the actual `_fence()` into composer/integrity owners. `execute` (`:579`) checks configuration/control again and enters the original factory read before exposing a provisional result; final checks and cleanup precede return.
- `packages/persistence/database.py:1629` separates coherent SQL schema capture from detached W3/W4 validation. `_capture_continuous_validation` (`:364`) returns a callback that invokes the configured reader on that exact detached snapshot after the transaction closes. `_load_nested_integrity_dependencies` (`:1655`) preloads modules before the snapshot, while validators still run against every current snapshot. These precedents shorten transactions; they do not defer lease acquisition or grant account authority to detached data.
- `continuous_account.py:1342–1430` resolves an index outside a transaction, captures its full composition under a fresh transaction, then resolves typed journal/checkpoint data outside SQL. `restore` (`:1637`) walks a fixed original prefix through those phases; `recheck_in_transaction` (`:1682`) freshly checks commit/lease/journal/composition data. These are real seams, but composition preparation calls into current daily ownership.
- `continuous_composition.py:1412` reads and checks historical evidence before capture, then calls `_historical_current`. That selects an original authenticated daily borrow or `_current` (`:533`), which performs a new daily snapshot read with `self.fence`. Capture subsequently rechecks that original current snapshot and sources. It cannot currently be called as a qualified unfenced pre-lease preparation.
- `durable_journal.py:282` explicitly prepares typed append/codec work before a database transaction. This is an existing transaction boundary for a different operation, not a pre-lease factory restore token or result cache.

## Why the obvious deferred-validation move fails the current contract

The coherent schema snapshot deliberately includes account leases, lease heads and releases alongside operational-control dependencies (`database.py:179–185`, capture at `:282`). Acquiring a writer lease changes those lease/head rows.

The configured reader's `_validate` (`continuous_integrity.py:1954`) calls its own fresh `_capture` (`:1893`), which revalidates the actual fence in the capture transaction. It requires that fresh original snapshot to equal the supplied schema snapshot exactly before entering `inspect_committed_observations` on the original head under `self.fence`. Therefore, simply capturing/preparing before acquisition and running the returned callback after acquisition fails `CONTINUOUS_SQL_SNAPSHOT_CHANGED`. Ignoring or rebasing the acquisition-induced difference would alter the exact-snapshot contract.

Daily capture is equally explicit: `_read_snapshot` (`daily_runtime_risk.py:1495`) requires an exact matching AccountFence, calls `coordinator.revalidate(fence)`, captures bounded rows, then issues an owner-bound `DailyRuntimeRawSnapshot` containing that receipt. Resolved daily snapshots retain raw ownership/seal identity. `_validate_original` (`continuous_integrity.py:1990`) establishes this current daily state and an original episode before validating account history and associations. Neither an arbitrary pre-lease decoded object nor a copied raw capture satisfies this ownership path.

## What remains possible without claiming an existing seam

Moving only construction/import work that has no fence dependency is not the same as moving the expensive retained decoding/identity validation, and the inspected evidence establishes no material benefit for doing so. The three retained configuration objects are already decoded before acquisition. Performing additional speculative decoding without consuming it through a qualified reuse path adds work rather than proving a saving.

The consequential decision, if the owner wants further investigation, is whether to introduce an explicitly provisional, bounded pre-lease preparation of fixed historical bytes/rows and a new original-owner handoff after acquisition. Such a design would have to specify which acquisition-induced lease changes are permitted, prove all other original bytes/rows/dependencies still match fresh captures, preserve original source/receipt/fence/entry-terminal ownership, and forbid adoption of later financial state. Existing receipt times or identities cannot be rebound to the new fence. The caller must not treat unqualified pre-lease data as validated authority.

That is new lifecycle and error-order behavior, not a small rescheduling of an existing public API. It would also need bounded pre-lease retained/temporary memory, Stop handling, changed-row/object/class/callback rejection, and fresh authority tests. Preserve the separate original limit families: the retained factory fixture uses a **60-second lease** and a **120-second operation wall timer** (`tests/integration/test_continuous_simulation_factory_outcome.py:323`, `:364`); its retained-run evidence records a **150-second parent limit where applicable** (`docs/reviews/2026-09-26-autonomy/factory-proof-original-retained-first.json`). That parent limit is not a CPU cap. The separate supervised genesis/initial-assignment worker uses the default **30-second wall, 30-second CPU and 512 MiB memory limits** because `request_for` supplies no overrides (`tests/integration/test_continuous_simulation_factory.py:68`; `packages/application/continuous_process.py:43`). The general process policy admits wall/CPU values only up to 120 seconds and applies the requested CPU value through `RLIMIT_CPU` (`continuous_process.py:55`, `:786`); it does not define a 150-second CPU allowance. Moving time outside `execute` must not be presented as reducing total startup or satisfying any of these distinct operation, parent or worker bounds.

No broad rewrite, SQL/fence skip, lease extension/renewal, unqualified snapshot import or new implementation is recommended here. The source investigation supports a concrete separate decision boundary, not approval or guaranteed performance benefit. The daily per-node resource rejection is an independent finding and provides no authority to pivot to this design.
