# Decision assessment: repeated daily snapshot identity traversal

Read-only assessment of the current autonomous-development source and preserved rejection evidence, 2026-09-26. **The proposed substitution/authority design is unapproved.** The owner-approved A2.3 pilot replaced one attempt-source fingerprint; it did not authorize replacing daily risk identity checks. Observational offline measurements that preserve all original calls and limits remain authorized by the original task; they do not require another owner decision. No implementation, fixture run, timing experiment, provider/access inspection or production change was performed for this assessment.

Production is unchanged from `2a9fc2c`; this assessment was prepared at diagnostic/evidence revision `26631c6`. Read [current status](../../STATUS.md) for subsequent results.

## Finding

No additional small, materially useful, fully behavior-preserving optimization is established by the evidence inspected. This is not a claim that every possible implementation has been exhausted. The concrete local alternatives already investigated are unsuitable:

- Replacing dataclass/mapping generator snapshots with comprehensions changed `StopIteration` chaining and field/value finalizer order. Both failures are preserved in `daily-identity-list-*-repro.txt`.
- Retaining the generator and using `list` instead of `tuple` regressed the finite workloads by about 1.0–1.5% (the `daily-identity-list-generator-probe.json` capture embedded in [rejected shortcut evidence](rejected-shortcut-investigation.json)).
- Frozen scalar membership changes live scalar-alias behavior; eager live membership changes short-circuit error behavior. The latter also regressed the sampled workloads by about 21–67%. `daily-native-membership-rejection.json` preserves concrete counterexamples rather than treating a microbenchmark as compatibility evidence.

Changing only the private factory's repeated daily-snapshot verification could be a defensible next experiment, but requires a separate consequential scope decision. A generic cache, replacement of `_assignment_identity_fields`, or automatic extension of the existing proof is not justified.

## Actual owners and callers

`SqlDailyRuntimeRisk._assignment_identity_fields` (`daily_runtime_risk.py:992`) constructs a fresh ordered identity vector. Exact tuples retain their children and are traversed in LIFO order with an identity-based visited set. Exact scalar leaves are skipped. Other objects use dataclass discovery and field reads first, then Mapping classification and `items()`. All dataclass fields participate, including private seal/owner fields. Aliases and cycles are supported; user getters, mapping hooks, reflection failures and generator failure/finalization behavior are observable.

The store's `_own` (`:876`) retains these vectors for resolved snapshots, prepared admissions, prepared assignments, assignment prefixes and prepared/retained attempts. `require_resolved_snapshot` (`:1245`) first calls `_resolved` (`:2647`), which preserves exact store ownership of both snapshot and raw capture plus their original seal bindings. It then compares a fresh full identity vector with `_resolved_originals[id(value)]` by length and `is`. Other consumers include admission/assignment/attempt/prefix validation, including in-transaction preparation guards. Those are financial publication boundaries, not an interchangeable cache opportunity.

The narrower existing factory seam is `SqlContinuousIntegrityReader._require_daily_graph` (`continuous_integrity.py:1507`): it calls `daily.require_resolved_snapshot(current)` twice, before and after attempt/observed source verification, while preserving `_require_graph` on both sides. Three such graph checks occur in each original daily borrow. This gives at most six candidate daily identity comparisons per borrow. The current profile's 99 `require_resolved_snapshot` entries and 109 identity-builder entries include other owners/roots and registration; they must not all be assigned to this proposed seam.

## Proposed substitution boundary — only if separately approved

1. Retain the public `require_resolved_snapshot`, generic identity builder, `_own`, all prepared/retained admission/assignment/attempt/prefix paths and every in-transaction caller literally unchanged.
2. Admit only an exact store-owned `ResolvedDailyRuntimeSnapshot` selected by the original HALTED factory operation and original registered daily episode. Run the existing complete public validation at entry before issuing any private daily proof.
3. At only the two existing daily snapshot calls in `_require_daily_graph`, and only when that graph check is entered through the authenticated original factory borrow, allow an explicit private daily-owner method to run the original `_resolved` ownership/seal prefix and a fresh qualified data-binding proof instead of constructing/comparing the large identity vector. Ordinary graph calls and missing/unsupported initial proof use the unchanged public method.
4. Keep both check positions. Do not coalesce them around callbacks or reuse the result of the first check for the second. Preserve all source/outcome guards, SQL/object observations, coordinator/fence checks, full entry/final validation, Stop and cleanup exactly where they are.
5. The daily owner needs an explicit operation/thread/episode/borrow/check-bound proof and single-use authority. Do not consume or reinterpret the existing attempt-source permit: it currently brackets a different single source check. Any new daily-use role must have its own reviewed finite lifecycle, original method/baseline binding, and failure poisoning. There is no ambient fast-path flag or public proof injection.

The exception/failure contract is an explicit delta: unsupported initial shapes fall back; an issued qualified graph whose structure or permitted behavior changes fails closed instead of executing changed hooks. Class/schema changes may be rejected more strictly than the original flat vector even when that vector would coincidentally stay equal. This must be accepted deliberately, not described as a universally compatible helper rewrite.

## The raw profile must differ from the attempt fingerprint profile

The existing `_factory_attempt_fingerprint` proof models `detached_journal_value`, whose mapping precedence, excluded fields and semantic leaves differ. Reusing its selector inventory would omit required daily identity state.

- Daily identity checks dataclasses before mappings, visits every field, and includes the entire nested resolved state rather than only the attempt fingerprint projection. No `_owner`/`_validated_values` exclusion is permitted.
- It compares identities, not canonical bytes. Exact Decimal/date/datetime/object leaves need identity preservation, not newly invented canonical/finite/UTC restrictions. Enum name/value and SQL table contents must not be silently promoted into a stronger semantic predicate where the original traversal treats the object as an opaque leaf.
- Only exact, ordinary, originally classified types can be admitted without running replacement hooks. Pin the consumed class/schema/field/accessor behavior and module/builtin lookup dependencies needed to prove the original traversal's dispatch and identity sequence. Unsupported subclasses, getters, custom mappings or unknown opaque types fall back before issuance. Either preserve cycle/alias meaning in the admitted profile or conservatively fall back on those shapes; never ignore an edge.
- Exact mapping proxies require qualified exact-dict backing. Their backing fields, order and identities are checked afresh, with original aggregate bounds before allocation.
- **The attempt proof's outer-tuple Mapping witness does not transfer.** This helper's exact-tuple fast path never calls `isinstance(tuple, Mapping)`. Any native Mapping witness must be established from the actual original traversal's consumed roles (for example an originally visited, non-dataclass opaque negative-classification leaf), under unchanged native classification/token evidence. Do not add calls merely to prime the ABC caches. If the required witness cannot be established within the qualified runtime and current bounds, return to full validation.
- Keep a finite profile for this predicate; do not build a generic graph attestation framework or traverse live SQLAlchemy/owner graphs simply because the identity vector contains their pointers.

## Lifetime and resource obligations

The daily store remains the issuer and original-value owner. Bind its exact `_seal`, snapshot/raw ownership and original saved identity-vector reference, together with the exact factory/episode/thread/borrow. Reject copied stores, proofs, snapshots, foreign-thread/operation use, reentrancy and retired reuse. A caught private-use failure must poison the enclosing original operation. Revocation must release all added graph/owner references even when guards or cleanup fail; no failure may reseal changed input.

Retire before handoff-structure retention, preserving original full final checks and the episode's existing identity-only cleanup. This new proof would overlap the current attempt proof during the episode. They must **jointly** fit the existing 16,384-container/131,072-binding allowance, including both data inventories, any additional behavior inventories, contexts, use records and temporary construction state. The observed attempt proof currently occupies 7,389 containers/66,263 bindings, leaving only 8,995/64,809 before new charges on that graph. These are measured shape-specific numbers, not a fresh allowance. Reject the proposed admission if it does not fit; do not introduce cross-proof deduplication or a larger cap as an incidental fix.

## Required adverse and acceptance evidence if approved

- Literal public-method/helper compatibility remains unchanged for all nonpilot callers, including generator exceptions/finalizers, dynamic alias changes, mapping/dataclass precedence, subclasses, aliases and cycles.
- Genuine registered factory use plus copied/foreign/retired/unregistered/reentrant denials; exact use count/positions; catches cannot rescue a poisoned operation.
- Deep daily data mutation after preceding guards and between the two daily checks; no accepted use after row reorder/add/remove, tuple/field replacement, schema/descriptor/method mutation, or original identity-vector/owner substitution. Unchanged original field identities continue to pass.
- Unsupported initial behavior falls back with the original read/error ordering and no extra user hooks. Native classification/proxy witness loss after issuance rejects; it never reprimes or reseals.
- Joint cap equality/overflow and construction-failure cleanup; no retained graph after retirement/owner loss; full entry/final observations and SQL/fence read counts remain unchanged.
- Original signed-history, process/restart, financial/source/artifact preservation and exact-source Linux/PostgreSQL acceptance under every existing limit.

Reject the experiment before production adoption if the full graph cannot be admitted within the shared caps, a finite predicate proof requires broad attestation or weaker checks, complete measured savings are negligible/negative, or original acceptance continues to fail without an evidenced narrow repair. Do not justify continued expansion from the profiler's apparent upper bound. A fresh owner decision would be required for this daily boundary even if the implementation can reuse some mechanical code from A2.3.
